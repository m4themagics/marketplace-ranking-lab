# Задание 00 — нулевая полоса для критерия C

**Бюджет:** один вечер, ~1,5–2 ч. **Фаза:** неделя 0, до kill-теста.
**Код:** `permutation_null_band` в [viability.py](../../src/mrl/data/viability.py) — stub.

## Зачем

`attribute_divergence` возвращает число. JS-дивергенция между двумя конечными выборками
больше нуля даже когда обе взяты из одного распределения — тем больше, чем реже атрибуты и
чем меньше когорты. Без нулевой полосы критерий C меряет размер когорты наравне с содержательным
сдвигом, а решение по датасету принимается по числу, у которого нет масштаба.

Сделать это надо **до** первого прогона на реальных данных. После — любая правка порога или
статистики выглядит как подгонка препрега задним числом, независимо от намерений.

## Что уже решено, не обсуждается

- C **не блокирует** датасет: низкий C означает, что новые когорты похожи на прежние, и у
  замороженного квантователя хорошие предпосылки обобщиться. Оба исхода публикуемы
  ([план](../../docs/development-plan.md), раздел «Неделя 0»).
- Решение принимается на уровне `product_code`; `article_id` — диагностика вариантов.
- `PASS_C_MIN_DIVERGENCE = 0.05` остаётся ориентиром и не трогается в этом задании.
- Выход функции уже зафиксирован типом `PermutationNullBand`: наблюдаемые значения,
  отдельные границы полос для `first_to_last` и `trend_slope`, число перестановок, seed и
  `min_cohort_size`. Менять контракт после прогона нельзя.

## Что решаешь ты до первой строчки кода

Четыре вопроса перечислены в docstring stub-а: что обменимо под нулевой гипотезой, для какой
статистики строится полоса, сколько перестановок и сторонний ли интервал, и как читать полосу
на 47 тысячах продуктов. Ответы записываются в рабочую запись ниже **до** реализации.

## Порядок работы

По [tests/README](../../tests/README.md): сначала падающий тест, потом минимальная реализация.

1. руками разобрать игрушечный пример: 3 когорты, 2 атрибута — куда попадёт наблюдаемое
   значение при перемешивании меток;
2. падающий тест: на синтетике без сдвига наблюдаемое значение внутри полосы;
3. падающий тест: на синтетике со сдвигом (jersey-tee → knitwear, как в существующих тестах) —
   снаружи;
4. реализация;
5. тест на failure mode: перемешивание атрибутов вместо меток когорт даёт слишком узкую полосу;
6. тест на детерминизм: один и тот же `seed` — одна и та же полоса.

## Определение готовности

- пункты 1–6 закрыты, `uv run pytest` и `uv run ruff check .` зелёные;
- можешь без кода объяснить, почему полоса — это линейка, а не ворота;
- можешь назвать failure mode, который поймал бы твой тест 5, и почему он правдоподобен;
- в трекере [LEARNING.md](../../LEARNING.md) строка «uncertainty и bootstrap» поднимается до
  уровня, который ты можешь защитить.

## Что в это задание не входит

Runner и препрег уже разведены на `gates` и `measurements`. В это задание по-прежнему не
входят скачивание данных с Kaggle и интерпретация реального результата: они начинаются только
после зелёных синтетических тестов.
